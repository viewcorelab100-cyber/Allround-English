## Interfaces

### AdminAccountAPI — Edge Function `create-admin`
*fulfills R-B1.1, R-T1.1, R-T1.2*

Request (from admin.html, caller must hold an admin session):
```
POST /functions/v1/create-admin
Headers: Authorization: Bearer <caller's admin JWT>
Body: { email: string, password: string, name: string }
```

Server-side behavior:
1. Verify caller JWT resolves to a `profiles` row with `role='admin'` (privilege-escalation guard) — reject otherwise
2. `auth.admin.createUser({ email, password, email_confirm: true })` using `service_role` key (server-side only)
3. Upsert `profiles` row: `role='admin'`, `name`, `is_active=true`

Response:
```
{ success: true, user_id: string } | { success: false, error: string }
```

Deactivation has **no dedicated Edge Function**. It is a direct client-side `UPDATE profiles SET is_active=false WHERE id=...` from admin.html, authorized by the existing "Admins can manage all profiles" RLS policy (no `service_role` needed — flagged in Ambiguities).
*fulfills R-B1.2, R-T1.3*

### GuideStorageAPI — Storage bucket `guide-attachments`
*fulfills R-B2.1, R-B2.2, R-B2.3, R-T2.1*

- New bucket `guide-attachments`: public read, admin-only write RLS (SQL migration, same pattern as `create-submissions-bucket.sql`)
- Thumbnail: `storage.from('guide-attachments').upload(...)` + `getPublicUrl()` → written into existing `guides.thumbnail_url` (no schema change to `guides`) — replaces the current `<input type=text id=guide-thumbnail>` URL-paste flow
- Attachment: same bucket, path convention `${guideId}/${filename}`, one `guide_attachments` row created per uploaded file
- Both upload paths reject client-side (pre-upload) any file where `file.size > 50 * 1024 * 1024`; no MIME/type restriction
- `guide-detail.html` reads `guide_attachments` by `guide_id` to render download links (no pagination needed — attachments per guide are low-cardinality; the R-T2.2 fetchAllRows rule applies only to future admin-side bulk listings across all guides, if built)

### SiteConfigScript — `site-config.js` (single shared script)
*fulfills R-B3.2, R-B3.3, R-B4, R-T3.2, R-T3.3, R-U2*

Injected into all 15 hardcoded live pages + `js/footer.js`, runs after `window.supabase` is available.

Reads:
- `YOUTUBE_URL` — hardcoded constant `"https://www.youtube.com/@allround_edu"` (not from DB, not admin-editable)
- `site_settings` rows for `recruit_tab_enabled`, `recruit_tab_url` (public-read query)

Mutates in DOM (attribute-level only, no structural/layout change):
- Every element marked `[data-youtube-link]` (nav menu item + footer icon anchor, 2 per page): sets `href=YOUTUBE_URL`, `target="_blank"`, `rel="noopener"`
- Every element marked `[data-recruit-tab]`: if `recruit_tab_enabled===true` and `recruit_tab_url` passes the scheme whitelist → removes `menu-title-disabled` class, sets `href`, `target="_blank"`; otherwise leaves the existing disabled/grey state untouched
- Requires the 15 pages + `footer.js` to add `data-youtube-link` / `data-recruit-tab` attributes to their existing `<a>`/`<span>` tags (markup-only addition, not a layout/CSS change — see Ambiguity 3)

## Invariants

- **INV-1**: `create-admin`'s `service_role` key is used server-side (Edge Function) only — never shipped to or invoked from the browser (R-T1.1, R-T1.2)
- **INV-2**: `create-admin` rejects any caller whose JWT does not resolve to `profiles.role='admin'` — blocks privilege escalation (R-T1.2)
- **INV-3**: Accounts with `is_active=false` are excluded from every student/roster listing query and blocked from login/admin access, while `role` and profile data remain intact (R-B1.2, R-T1.3)
- **INV-4**: Guide thumbnail/attachment uploads reject any file where size exceeds 50MB, enforced client-side before upload; no file-type/MIME restriction (R-B2.3)
- **INV-5**: `site-config.js` only writes `href` values whose scheme is `http:` or `https:`; any other scheme (e.g. `javascript:`) is dropped and the target element stays inert/disabled (R-T3.3)
- **INV-6**: `site-config.js` / `site_settings` injection changes only `href`/`class`/`target` attributes on existing DOM nodes — never alters page layout or CSS (R-T3.2)
- **INV-7**: Any admin-side listing over `lesson_progress`-scale tables (guides, attachments, profiles) uses the existing `fetchAllRows()` pagination helper once row counts can exceed 1000 (R-T2.2)
- **INV-8**: The YouTube URL is a code-level constant in `site-config.js`; admin has no UI to edit it (R-B4)

## Ambiguities carried into contract (see return JSON for main-agent triage)

1. `is_active` boolean vs `role='disabled'` — this contract picks `is_active` boolean (role stays `'admin'`) to avoid breaking `isAdmin()`/`checkAdminAccess()` role-branch logic. OD-1 named both options.
2. Deactivation was not assigned an Edge Function by R-T1 (only creation was). This contract routes deactivation through the existing "Admins can manage all profiles" RLS via direct client UPDATE, no `service_role` involved.
3. The 15 hardcoded live pages have no existing hooks for a shared script to target. This contract assumes `data-youtube-link` / `data-recruit-tab` attributes get added to existing tags — a markup-only change, not a layout change, but it does touch all 15 pages + footer.js.
4. `guide_attachments` as a new table (vs. a JSON array column on `guides`) — chosen to support multiple attachments per guide cleanly.
5. `site_settings.value` typed `jsonb` (vs `text`) — chosen so one column can hold both the boolean and the string URL setting introduced here, and future keys without a schema change.
